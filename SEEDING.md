# Seeding scheme for the q_value dataset generation

Written 2026-10-19T20:55Z.
Status: design agreed with the user; no code implements it yet (BUG-007, OBS-016 in `BUGS.md`).
Adapted from a `SEEDING.md` that came from another repository (a GRB paper codebase); this file is the project's own record and replaced that copy.
Rules come from `CLAUDE.md` §14 (determinism) and §6 of `WORKING_CONVENTIONS.md` (a generated file carries its provenance).

## Why

The `ml-gw-search` generator (`mlgwsc-1/gen.py`) is unseeded, and the dataset in use, `combined_repackaged.hdf`, cannot be regenerated bit-for-bit.
Two causes are verified by code read:

- `np_gen = np.random.default_rng()` has no seed and no CLI option.
- pycbc's noise draw (`frequency_noise_from_psd`) and sky-location draw (`UniformSky.rvs`) use the legacy global `numpy.random`, so seeding `np_gen` alone leaves them random.

Seed literals are also scattered: `42` in the six `configs/*.yaml` and as a `train.py` default, `0` in `loader.py` and the tests, `132354` in `re_package_hdf.py`.

## `MASTER_SEED`

```
MASTER_SEED = 3021456217
```

Provenance, reproduced verbatim:

```
$ python3 -c "import secrets, datetime; print(secrets.randbits(32)); print(datetime.datetime.now(datetime.timezone.utc).isoformat())"
3021456217
2026-10-19T20:50:33.343047+00:00
```

Drawn on host `thinkpad-t530` from the OS CSPRNG, not from NumPy, so it depends on no generator state.
It is this project's own value: never reuse the master seed of another repository.
The constant is to be defined once, in the generator repository (`ml-gw-search`), when the scheme is implemented; this file is the record of its value and origin.

## Derivation: one key per file, stream, and purpose

Every seed is a `numpy.random.SeedSequence` keyed by `MASTER_SEED` and an explicit integer tuple.
The tuple is the key, so a seed never depends on call order, process order, machine, or checkout path.

```python
def seed_seq(file_index: int, stream: int, purpose: int) -> np.random.SeedSequence:
    return np.random.SeedSequence(MASTER_SEED, spawn_key=(file_index, stream, purpose))
```

| Level | Values | Meaning |
|-------|--------|---------|
| `file_index` | 0, 1, 2, … | one output file (the README generates 50 files, one process each) |
| `stream` | 0 = training, 1 = validation | separate streams, so changing the training count never shifts the validation data |
| `purpose` | 0 = injection `rng`, 1 = pycbc global state, 2 = SNR draw | independent draws that must not share a stream |

Checked on this machine (2026-10-19, numpy 2.2.6, with the master above):

- 300 keys (50 files × 2 streams × 3 purposes) give 300 distinct states.
- A rebuilt key reproduces its draws, and the validation stream differs from the training stream.
- `SeedSequence(MASTER_SEED, spawn_key=(f,)).spawn(2)` equals the explicit `(f, 0)` and `(f, 1)` keys, and child *i* does not depend on how many children are spawned, so files 50 onward can be added without changing files 0–49.

## Usage pattern (decided: option A for pycbc)

Each of the two streams of a file does, once, at its start:

```python
rng = np.random.default_rng(seed_seq(file_index, stream, 0))       # injection parameters
np.random.seed(seed_seq(file_index, stream, 1).generate_state(4))  # pycbc noise and sky draws
```

and then threads that one `rng` through every injection draw in the stream.

- Never pass `seed=` to a pycbc call inside the sample loop.
  The same seed per call gives identical noise on every call, and also identical H1 and L1 noise within a sample (verified: the same seed reproduces the same noise).
- The global `numpy.random.seed` call is made once per stream, with a state distinct from every other stream, which is why it does not recreate the reseed-per-iteration bug.
  It is the one place that deviates from "thread one generator", because pycbc cannot be handed a generator.
- Rejected: drawing a 32-bit seed per call from the `rng` (about 24–34% chance per file that two noise calls share a seed).
- Not chosen now: spawning a per-call seed array from the `rng` (option B), and rewriting the noise and sky draws to use `np_gen` (option C, the purest design, to be revisited if the global-state deviation proves a problem).

## What each generated file records

A generated file must be checkable without its generating script, so these go in the HDF attributes (and not only in a registry):

- `master_seed`, `file_index`, and the three `(file_index, stream, purpose)` keys used.
- The `gen.py` arguments (approximant, noise source, detector count, sample length, sample counts).
- The generator repository's git SHA, and the python, numpy, pycbc, and h5py versions.
- The UTC time of generation, and the host.
- The column names of `params`, matching what the file actually contains (BUG-008).

Any seed registry or table for the paper is generated by a script from these attributes, never hand-assembled (`WORKING_CONVENTIONS.md` §6).

## Determinism check (not yet run)

Before any full generation, on a shrunken workload that is reverted afterwards, and only with the user's go-ahead on a machine other than `thinkpad-t530`:

1. Generate one file twice from the same `file_index`; compare `noises`, `waveforms`, and `waveform_params` for exact equality.
2. Generate with a different `file_index`; the arrays must differ.
3. Generate with a changed training count; the validation arrays must stay identical.
4. Check that H1 and L1 noise within a sample differ.

Falsified by: any difference in step 1 or 3, any equality in step 2 or 4.
Compare arrays, not file bytes, since whether h5py writes byte-identical files is unknown.
Differences only at float-rounding level (for example from FFT threading) are a decision point for the user, not something to resolve quietly.
The generator repository has no test suite, so this is covered only by an ad-hoc check unless a test is added.
